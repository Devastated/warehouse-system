# «Склад-Пульт» — система учёта складских товаров (полный проект)

Микросервисная система для учёта товаров на складах: справочник товаров,
склады и остатки, операции прихода/расхода с историей, сводные отчёты
и **веб-пульт диспетчера**, который показывает всё это на экране и печатает
результат каждой операции в терминале.

Технологии: **.NET 8 (ASP.NET Core Minimal API)**, **YARP** (API Gateway),
**PostgreSQL 16**, **Docker / Docker Compose**, а для интерфейса — чистые
**HTML + CSS + JavaScript** без сборки, npm и внешних CDN.

> Стиль интерфейса намеренно отличается от витринного проекта-примера:
> не «тёмное стекло с золотом», а светлый промышленный терминал — жёсткие
> углы, моноширинная типографика, штрих-кодовая сетка, штрафная полоса,
> штамп «INVENTORY REPORT» и лампочки диагностики.

---

## 1. Что проверить в первую очередь

1. `docker compose up -d --build` — поднимается весь стек.
2. Открыть **http://localhost/** — веб-пульт с живыми данными.
3. Нажать **«Заполнить демо»** — появятся товары, склады и операции.
4. Нажать **«Текстовый отчёт»** — откроется отчёт в читаемом виде
   `GET /api/reports/text`.
5. Провести приход/расход в форме **«Пульт операций»** — результат
   напечатается в **«Терминал вывода»**, таблицы обновятся сами.
6. Посмотреть блок **«Диагностика сервисов»** — это запрос к `/status`,
   который реально опрашивает health-эндпоинты всех сервисов.
7. `curl http://localhost:8080/status` — тот же диагностический JSON.

Если Docker не запущен, пульт не остаётся пустым: он показывает явно
помеченный **«ДЕМО-ДАННЫЕ»** срез и локально сформированный текстовый отчёт.
Режим в шапке всегда честно сообщает, живой это API или демо.

## 2. Назначение проекта

Проект демонстрирует полноценный учебный full-stack-продукт:

- **Веб-пульт** — сводная таблица остатков, журнал операций, формы ввода,
  терминал вывода, отчёт и диагностика.
- **Бэкенд** — пять независимых .NET-микросервисов, каждый отвечает
  за свою область.
- **Хранилище** — PostgreSQL: одна база `app`, отдельная схема на сервис.
- **Единая точка входа** — gateway отдаёт интерфейс и проксирует `/api/*`.
- **Отчётность** — отдельный сервис собирает данные по HTTP и умеет
  выводить их как JSON и как обычный текст.

Данные страниц берутся из API, а не из захардкоженных массивов. Исключение —
только помеченный демо-режим для обучения и просмотра без Docker.

## 3. Архитектура

```
                 ┌──────────────────────────────────────────┐
                 │  Браузер: web/ (HTML + CSS + JS)          │
                 │  остатки · операции · терминал · отчёт   │
                 └──────────────────┬───────────────────────┘
                                    │ http://localhost:8080/
                 ┌──────────────────▼───────────────────────┐
                 │ gateway (YARP + static files), порт 8080 │
                 │  /            → веб-пульт                │
                 │  /api/*       → нужный сервис            │
                 │  /status      → опрос health-эндпоинтов  │
                 └───┬──────────┬──────────┬──────────┬─────┘
                     │          │          │          │
        /api/products│  /api/warehouses,/api/inventory  /api/movements  /api/reports
                     ▼          ▼          ▼          ▼
              ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
              │ products │ │inventory │ │movements │ │ reports  │
              │  :5001   │ │  :5002   │ │  :5003   │ │  :5004   │
              └────┬─────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘
                   │            ▲            │            │ HTTP-агрегация
                   │   HTTP     │   HTTP     │            │ (без своей БД)
                   └────────────┴────────────┤            │
                                            ▼            ▼
                              ┌──────────────────────────────────┐
                              │ PostgreSQL 16, база app           │
                              │ схемы: products, inventory,       │
                              │        movements; volume db_data  │
                              └──────────────────────────────────┘
```

Все контейнеры находятся в сети `warehouse-net`. Снаружи доступен только
gateway; сервисы обращаются друг к другу по именам контейнеров.

### Сценарий операции прихода

1. Браузер отправляет `POST /api/movements` через gateway.
2. `movements-service` делает `GET` в `products-service` — товар существует.
3. `movements-service` делает `POST` в `inventory-service` — остаток меняется
   (расход не даёт уйти в минус).
4. Операция сохраняется в `movements.movements` со снимком остатка.
5. Gateway возвращает ответ; пульт печатает его в терминале и обновляет таблицы.
6. `reports-service` при следующем обновлении пересобирает сводку и текстовый отчёт.

## 4. Состав и порты

| Компонент | Порт | Назначение |
|---|---|---|
| `gateway` + веб-пульт | **8080** | Интерфейс, `/api/*` прокси, `/status` |
| `products` | 5001 | Справочник товаров: SKU, название, единица |
| `inventory` | 5002 | Склады и остатки, защита от отрицательного остатка |
| `movements` | 5003 | Приход/расход, оркестрация, история операций |
| `reports` | 5004 | JSON-сводка, срез остатков, текстовый отчёт |
| `db` | 5432 (внутри сети) | PostgreSQL 16, база `app`, volume `db_data` |

Каждый сервис — отдельная папка, отдельный Dockerfile, конфигурация через
переменные окружения (`DB`, `PRODUCTS_URL`, `INVENTORY_URL`, `MOVEMENTS_URL`,
`REPORT_URL`, `LOW_STOCK`). Ничего критичного не захардкожено.

## 5. Запуск

Нужны только Docker Desktop / Docker Engine с плагином Compose. Java и Node
локально ставить не обязательно.

```bash
docker compose up -d --build
docker compose ps
```

После запуска открыть **http://localhost/**.

Полезные команды:

```bash
docker compose logs -f                          # все логи
docker compose logs -f gateway reports          # конкретные сервисы
docker compose restart                          # перезапустить всё
docker compose down                             # остановить, данные сохранятся
docker compose down -v                          # остановить и удалить данные БД
```

При первом старте сервисы сами создают свои схемы и таблицы. Повторный старт
данные не очищает, пока не выполнен `down -v`.

## 6. Веб-пульт

Интерфейс лежит в `web/` и попадает в образ gateway как статические файлы.
Сборка не нужна: `index.html` + `styles.css` + `app.js`.

| Блок | Что делает |
|---|---|
| KPI-плитки | Товары, склады, суммарный остаток, приход, расход, позиции «на контроле» |
| Остатки | Сводная таблица «склад → товар → количество → состояние», поиск по складу, SKU и названию |
| Журнал операций | История прихода и расхода с фильтром по типу, датой и снимком остатка |
| Пульт операций | Формы: провести приход/расход, добавить товар, добавить склад |
| Терминал вывода | Каждое действие печатает строку с временем и ответом API; логи можно очистить |
| Текстовый отчёт | Открывает `/api/reports/text` (в демо-режиме — локально сформированный отчёт) |
| Диагностика | Статус, HTTP-код и время отклика каждого сервиса из `/status` |
| Демо-заполнение | Идемпотентно добавляет примеры товаров, складов и операций |
| Автообновление | Данные подтягиваются каждые 15 секунд; есть кнопка ручного обновления |

### Стиль

В отличие от примера с витриной крафтового пива, здесь нет glassmorphism,
мягких теней, анимированных частиц и вычурных display-шрифтов. Вместо этого:

- светлая «бумажная» подложка с технической сеткой;
- моноширинный шрифт и капитель для всех подписей;
- жёсткие 2-пиксельные рамки и «жёсткие» тени без размытия;
- оранжево-графитовая штрафная полоса и штамп документа;
- полосатые индикаторы, лампочки статуса и чёрный терминал с бегущим курсором.

Это не косметика: плотная табличная подача соответствует задаче учёта остатков.

## 7. Отчёты и вывод

`reports-service` — пятый микросервис. Он не хранит данные, а запрашивает
другие сервисы по HTTP. Если один из них недоступен, отчёт всё равно
формируется, а проблема попадает в раздел «Предупреждения».

| Метод | Путь | Что возвращает |
|---|---|---|
| GET | `/api/reports/summary` | KPI, срез остатков, низкие остатки, последние операции, warning-и |
| GET | `/api/reports/stock` | Готовый join: склад + товар + количество + состояние |
| GET | `/api/reports/text` | Текстовый отчёт `text/plain; charset=utf-8` |
| GET | `/api/reports/health` | Проверка сервиса отчётов |

Пример вывода `/api/reports/text`:

```text
================================================================

================================================================

  Товаров в справочнике .........     4
  Складов .......................     2
  Общее количество на складах ...   117 шт
  Операций прихода ..............     2
  Операций расхода ..............     2
  Позиций с низким остатком .....     2 (порог 5 шт)

--- ОСТАТКИ ПО СКЛАДАМ -------------------------------------

    SKU-001      Кабель HDMI 1м                  70 шт  [НОРМА]
```

## 8. Диагностика сервисов

`GET /status` на gateway — не статичная картинка. Он параллельно опрашивает
четыре health-эндпоинта и возвращает для каждого статус, HTTP-код и время
отклика. Ошибка одного сервиса не ломает ответ: общий статус становится
`degraded`, остальные карточки всё равно заполняются.

Проверка из PowerShell:

```powershell
$s = Invoke-RestMethod http://localhost:8080/status
$s.status
$s.services | Format-Table service, status, responseMs, httpCode
```

## 10. Проверка системы

### Сначала интерфейс

1. `http://localhost/` — пульт показывает данные, а не заглушку.
2. Кнопка **«Заполнить демо»** → в терминале строки об успешном создании.
3. Форма **«Пульт операций»** → новая строка в журнале и изменение остатка.
4. **«Текстовый отчёт»** → текст с итогами и разделом «Требует внимания».
5. Блок диагностики → все четыре лампочки зелёные.

### Затем API

```bash
curl http://localhost:8080/health
curl http://localhost:8080/status
curl http://localhost:8080/api/reports/summary
curl http://localhost:8080/api/reports/text
```

Ожидаемый `-i` для текстового отчёта:

```text
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
```

### Персистентность

```bash
docker compose down
docker compose up -d
curl http://localhost:8080/api/warehouses/1/stock
```

Остаток сохраняется: данные живут в volume `db_data`.

## 11. Решения и бизнес-правила

- **Изоляция данных.** Один сервер PostgreSQL, база `app`, но схемы
  `products`, `inventory`, `movements`. Сервисы не лезут в чужие таблицы.
- **Остаток не уходит в минус.** Проверка в SQL-условии `quantity + delta >= 0`
  плюс `CHECK (quantity >= 0)` и понятная ошибка `400 insufficient stock`.
- **Горячая замена данных.** `reports-service` не имеет своей базы и всегда
  читает актуальные данные через API, поэтому отчёт не расходится с пультом.
- **Устойчивость интерфейса.** Если API недоступен, пульт показывает демо-срез
  с явной пометкой, а не пустые таблицы и не падает с необработанной ошибкой.
- **Идемпотентное демо.** Повторное нажатие «Заполнить демо» не создаёт дубли:
  товары проверяются по SKU, склады — по названию, операции — по факту наличия
  истории.
- **Порог низкого остатка** настраивается переменной `LOW_STOCK` (по умолчанию 5).
- **C4-схема.** Исходная схема ядра бэкенда:
  [docs/architecture.drawio](docs/architecture.drawio) и
  [docs/architecture.png](docs/architecture.png). Обновлённая диаграмма
  контейнеров с веб-пультом и сервисом отчётов:
  [docs/architecture-v2.drawio](docs/architecture-v2.drawio). Уровни C4:
  контекст, контейнеры, компоненты.

## 14. Честные ограничения

- Демо-режим в браузере использует локальный массив данных: он нужен только
  для обучения и не изменяет PostgreSQL.
- `reports-service` агрегирует данные по HTTP; это учебный вариант без
  transaction/outbox. При частичном отказе сервисов в отчёте появится
  предупреждение, но цифры могут быть неполными.
- Реальной аутентификации и ролей нет: это учебный стенд без доступа к БД из браузера.
- Порт 8080 должен быть свободен; иначе измени маппинг в `docker-compose.yml`.
- Текстовый отчёт формируется на сервере при каждом запросе, без кэша —
  это маленькая система, и свежесть важнее экономии ресурсов.
